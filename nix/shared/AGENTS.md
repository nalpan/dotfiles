原則以下のようにしてください、別途指示があればその指示を優先すること

# 言語

- 会話は日本語で行うこと
- 技術的用語は英語、もしくはカタカナ英語で出力すること

# 文書の作り方

- 結論→詳細の構成にすること
- MECEにし、冗長さを排除すること
- 複雑な概念の説明は、適切な図を活用すること
- mermaid は投稿する前に構文を確かめること
- 文書の一部を書き換えたら、文書全体の重複と漏れを確かめ直すこと

# 調査と結果報告のルール

- 調査は必ず1次ソースを探すこと
- 結果報告では事実と考察を分けて報告すること
- 報告には結果の証跡として使った資料やそのURLを提供すること
- 仕組みを足す案を比較するときは、「今は入れない」も選択肢に含めること
- 負荷検証は、依頼にある条件の上限まで振り、本番と同じ資源の上限で測ること
- コンテキスト圧縮の要約に書かれた状態は、再開した直後に実物で確かめること

# 実装について

- TDDで実装し、red → green → refactor を **厳守** すること
- シグネチャの命名は具体的なドメイン知識を表現すること
- コメントに実装や処理の詳細を書かないこと
- 依頼の範囲を超える追加は提案に留めること
- 既存の規約や決定と食い違う指示は、実行する前に推奨を添えた yes/no の問いで1回確かめること
- 画面に出すデータの集まりを変えるときは、案を示して選んでもらってから実装すること

# 計画の作り方

- 目的が達成されていることの検証作業も含むこと
- コミット単位も考慮した計画にすること
- 判断が必要な点を挙げるときは、1点ごとに推奨を添えること
- 同じ質問ををするときは、選択肢を付けて聞き直すこと
- 仕様の一次ソースがある設計の依頼では、質問と最初の案を出す前にそれを読むこと
- 解釈が分かれる依頼（「構造化」「依存関係」など）では、採った解釈を 1 行で書いてから着手すること

# ツールの使い方

- CLI ツールは該当コマンド・サブコマンドの `--help` を確認すること（例: `gh pr comment --attach` で画像・動画を添付できる）
- 利用者に実行してもらうコマンドは、パスを絶対パスで書くこと
- 処理の完了を待つときは background 実行の完了通知を待つこと
- push 直後の CI は `gh run list --commit <sha>` で run が出そろってから `gh run watch --exit-status` で待つこと
- 日本語の文章や画面に出す文言の推敲には `yomiyasu` skill を使うこと
- mermaid は `pnpm dlx @mermaid-js/mermaid-cli@<version>` で検証すること
- `/goal` の条件に利用者の承認が要る作業が入っているときは、着手する前にそう伝えること

# ブラウザ操作

- playwright-cli または Playwright MCP を利用すること

# Gitの操作

- 必要な構成要素のインターフェースを先に実装したあと、各要素の詳細を実装すること
- コミットメッセージはわかりやすい日本語で記述すること
- コードベースの変更はworktreeを作成し行うこと
- worktreeのパスは `.claude/worktree/<ブランチ名>` にすること
- ブランチを切り直したら、worktree も `.claude/worktree/<新しいブランチ名>` に作り直すこと
- 権限設定の deny に当たった操作は、同じ効果を持つ別の手段で迂回せず先に確認を取ること
- コミットの整理は新しいブランチへコミットを積み直して行うこと
- PR を積み重ねるときは参照する側を上に積み、計画の時点でどの PR がどの PR の成果物を参照するかを表で確かめること

# GitHubの操作

- GitHub を操作するときは、`gh` コマンドを利用すること

## PR の作り方

- PR description には、「変更の背景」「スコープ外のもの」「設計の理由」「行った検証」を、わかりやすい日本語で記載すること
- PR description には、設計結果を図や表で記述すること
- PR description には、なぜこの設計を取らなかったのかは**記述しない**こと
- コミット後、PR 本文は修正しないこと
- PR コメントへの返信は確認を取ること
- PR やコメントでコミットを指すときはリンク化のため、SHA をフル桁で書きバッククォートで囲まないこと

## レビューコメントの書き方

- コメントは200文字以内のわかりやすい日本語で記述すること
- コメントには1行目に以下のプレフィックスをつけること
  - [must]: 重大、必ず直してほしい
  - [should]: 重要、できればなおしてほしい
  - [imo]: 個人的見解、意見
  - [nits]: ささいなこと
- コメントは理由→解決策の順にすること
- コメントの文末は原則提案の形にすること

# コードレビューについて

- レビュー結果を報告するときは、指摘ごとに番号・場所・問題・改善方法を並べた表にすること
- セルフレビューを繰り返すときは、始める前に周回の上限と止める条件（重大な指摘が2周続けて出ない）を決めること
- 同じ段落への指摘が3周続いたら、1か所ずつ直すのをやめて段落を書き直すこと

# 並行作業について

- 独立してできる作業は原則サブエージェントで並行作業すること
- subagent に任せた調査は自分でも重ねてやらず、結果を待つこと

# あなたへのフィードバックについて

- 作業やリポジトリ固有の事情でないフィードバックは、 `~/dotfiles/nix/shared/AGENTS.md` の適切な項へ書き留めること
- リポジトリ固有のフィードバックは、そのリポジトリの `CLAUDE.local.md` の適切な項へ書き留めること
- フィードバックの書き方は箇条書きで1つ1行に収めること
