原則以下のようにしてください、別途指示があればその指示を優先すること

# 言語

- 会話は日本語で行うこと
- 技術的用語は日本語訳せず、英語のまま出力すること

# 文書の作り方

- 結論→詳細の構成にすること
- MECEにし、冗長さを排除すること
- 複雑な概念の説明などは図を活用すること

# 調査と結果報告のルール

- 調査は必ず1次ソースを探すこと
- 結果報告では事実と考察を分けて報告すること
- 報告には結果の証跡として使った資料やそのURLを提供すること

# 実装について

- TDDで実装し、red → green → refactor を **厳守** すること
- シグネチャの命名は具体的なドメイン知識を表現すること
- コメントは1行で簡潔に留めること、実装や処理の詳細は書かない

# 計画の作り方

- 目的が達成されていることの検証作業も含むこと
- コミット単位も考慮した計画にすること

# ブラウザ操作

- playwright-cli または Playwright MCP を利用すること

# Gitの操作

- 必要な構成要素のインターフェースを先に実装したあと、各要素の詳細を実装すること
- コミットメッセージは日本語で記述すること
- コードベースの変更はworktreeを作成し行うこと
- worktreeのパスは [作業ディレクトリ]/.claude/worktree/[ブランチ名] にすること

# GitHubの操作

- GitHubを操作するときは、`gh` コマンドを利用すること

## PR の作り方

- PR description には「変更の背景」「行った検証」を記載すること
- PR description には設計結果を図や表で記述すること
- PR description にはなぜこの設計を取ったのかを記述すること
- PR description なぜこの設計を取らなかったのかは**記述しない**こと
- PR 本文は修正しないこと
- PR コメントへの返信は確認を取ること

## レビューコメントの書き方

- コメントは日本語200文字以内とすること
- コメントには1行目に以下のプレフィックスをつけること
  - [must]: 重大、必ず直してほしい
  - [should]: 重要、できればなおしてほしい
  - [imo]: 個人的見解、意見
  - [nits]: ささいなこと
- コメントは理由→解決策の順にすること

# あなたへのフィードバックについて

- 作業単位固有でないフィードバックは `~/dotfiles/nix/shared/AGENTS.md` へ書き留めること
- フィードバックの書き方は箇条書きで1つ1行に収めること
